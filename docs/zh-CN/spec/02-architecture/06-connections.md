# 连接 目标架构

- 状态：目标规格；尚未实现
- 决策：D660 / ADR 0320，由 D661、D662 扩展
- 范围：让智能体从本机操作其他机器与设备
- 事实来源：`03-runtime/23-connections-protocol.md`
- 英文源规格：[英文源规格](/spec/02-architecture/06-connections)

## 1. 范围与状态

本文规定 **连接（Connections）** 的架构：一组**出向**的、归用户所有的目标
—— 经 SSH 的远端 shell、一个串口设备、一个 telnet 端点、一个原始 TCP 套接字 ——
智能体可以在其上执行命令、读取、写入。

当前发布版本中这一切都尚未实现。`连接` 目的地、设置卡片、`connection.*` 宿主
方法与 `Connection` / `Console` 两个工具都是目标工作。本文不改变
`00-baseline.md`、ADR 0004 或 ADR 0205 所冻结的 MVP 边界。

该能力让一位已认证的本地用户可以：

- 手工登记一个目标，并长期保留；
- 看到它的状态、最近一次探测、最近的活动；
- 让智能体在它上面执行命令、上传下载文件，对字节流目标还可以开会话收发字节；
- 一道总开关关掉整个面，或逐个目标关；
- 读到「谁在哪台机器上跑过什么」的审计记录。

该功能**不是**终端模拟器，**不是**会话管理器，**不是**任意网络代理，
**不是**远程桌面。§10 把这些排除项写成了要求，而不是偏好。

## 2. 设计原则

1. **这是把已有能力结构化，而不是新建一种能力。** `Bash` 工具本来就能在本机
   执行 `ssh host '…'`，因为它能执行任何命令。连接加上的是：具名目标、逐目标
   策略、主机密钥校验、审计轨迹，以及一个用户能看见的界面。它没有放宽智能体
   能触及的范围。
2. **目标是归用户所有的数据。** 一条配置由人在界面上创建、编辑、启用、删除。
   面向智能体的方法里没有任何一个能创建、编辑、启用或删除配置。这是按方法面
   保证的，不是按调用者身份判断的。
3. **面向智能体的那一面默认关闭。** 一道总开关管住所有面向智能体的方法与两个
   工具。每条目标另有自己的开关，因此可以「这台机器可达、那台不可达」。
4. **`exec` 与本地 `Bash` 同构。** 一次调用一个进程、一个结果信封、stdout 留头
   stderr 留尾用同一套输出预算，非零退出码作为数据而不是错误上报。同一种事情
   不该让智能体学两套约定。
5. **字节流目标是另一种原语。** 串口、telnet、原始 TCP 没有命令边界，也没有
   退出码。传输层声明自己能做什么，做不到的方法**按名字**拒绝，而不是含糊地
   失败。
6. **这里不实现协议栈。** SSH、SFTP 与端口转发都用系统自带的 OpenSSH 程序。
   用户的 `~/.ssh/config`、agent、跳板机、`known_hosts` 与他们自己的终端里完全
   一致地生效。
7. **秘密永不跨越模型边界。** 口令与密钥路径存在宿主的秘密库里。任何面向智能体
   的方法都不返回它们，任何审计记录都不存放它们。
8. **开关关掉所有面向智能体的门；面向用户的门始终敞开。** 开关关闭时，智能体
   既不能枚举目标，也不能让本机拨出去 —— `probe` 不是读操作，它会建立连接并
   认证，因此让它与 `exec` 共用同一个判定，才是「关」真的意味着关。面向用户的
   方法从不设闸，因为看到目标正是用户决定开启它的依据。
9. **宿主是事实来源。** 活动、状态与审计轨迹都是宿主状态，渲染层只负责显示。

## 3. 与远端智能体控制的关系

现在有两件事都是「连到另一台机器」。它们不是同一件事，规格不许可把它们搅在一起。

| | 连接（`connection.*`） | 远端智能体控制（`RACP`） |
|---|---|---|
| 回答的问题 | 「在那台机器上跑这条命令」 | 「把**我**放到那台机器上跑」 |
| 智能体循环在哪 | 这里 | 那里 |
| 远端有什么属于我们 | 什么都没有 | 一个 `pi-host`：会话、轮次、工具 |
| 工作区归谁 | 不归谁；就是目标自己的 shell | 远端 Agent Host |
| 传输 | 系统 `ssh`，或一条字节流 | SSH 隧道里的 `RACP-WS` |
| 状态 | 目标规格，本文 | 已实现的目标工作，ADR 0205 |

想交互式地在一个远端 Linux 盒子上驱动工程的人，要的是远端智能体控制。想让本地
智能体去重启那台机器上的一个服务、把构建产物拷到设备上、或从串口读一个传感器
的人，要的是连接。同一个主机上两者可以并存，§9 记录了它们的收敛点，以免长出
两套互不兼容的凭据存储。

## 4. 为什么这一层落在 Rust host-core

这一层是 host-core 的一个模块，与 `computer/` 并列，理由有四条。

1. **输出通路已经在那里。** 分流预算、溢出落盘、行数与字节上限、超时阶梯、
   中止时的进程组回收，全都在 `tools/` 里。一个在 TypeScript 里重新实现这些的
   远端 `exec`，恰恰会在最要紧的几种情况下走偏 —— 刷屏的命令、挂住的命令、
   用户中断的轮次。
2. **归属。** SQLite、秘密库、权限、审计记录都是 host-core 的。一条配置就是
   一条持久化记录加上一个秘密，两者都归它。
3. **冻结的进程模型。** AGENTS.md §4 要求 Electron Main 保持为薄编排层，并禁止
   渲染层直连 SQLite。把一整套 SSH 子系统放进 Main，两样都不满足。
4. **先例。** `computer/` 已经确立了形状：纯逻辑（几何、参数解析、策略）与平台层
   分开；平台层在服务不了的平台上**显式报不支持**而不是静默降级；两扇门共用
   同一个参数解析器，因此方法与工具对同样的输入给出同样的拒绝。

## 5. 传输抽象

两层能力，因为各类目标并不共享同一种形状。

```text
Transport
├── kind:           ssh | serial | telnet | raw-tcp
├── capabilities:   { exec, transfer, stream }
├── probe()                       连通性、认证、主机密钥
├── exec(command) -> ExecResult   仅在 capabilities.exec 时
└── open_stream() -> StreamHandle 仅在 capabilities.stream 时
```

| 种类 | `exec` | `transfer` | `stream` | 凭据 |
|---|---|---|---|---|
| SSH | 有 | 有（SFTP） | 有 | 密钥、agent 或口令 |
| 串口 | 无 | 无 | 有 | 无 |
| Telnet | 无 | 无 | 有 | 登录提示，或无 |
| 原始 TCP | 无 | 无 | 有 | 无 |

`ExecResult` 就是本地 `Bash` 的结果：`exitCode`、`stdout`、`stderr`、
`truncated`，以及预算被超出时的溢出文件路径。非零 `exitCode` 不是错误。

`StreamHandle` 是每条打开流一个的有界内存环形缓冲：写入的字节、读出的字节、
回滚上限，以及一个单调序号，让读者能把「空档」与「安静」区分开。它不是终端：
没有光标、不解转义序列、没有备用屏。

SSH 的具体约定：

- `ssh`、`scp`、`sftp` 都以系统自带程序的方式 spawn。Windows 自带
  `OpenSSH_for_Windows`；Unix 用登录 `PATH` 上的 `ssh`。
- 不覆盖用户自己的配置。配置里显式给出的主机、端口、用户、密钥文件以选项形式
  传入并优先，其余全部继承。
- **不假设连接复用。** `OpenSSH_for_Windows` 不支持 `ControlMaster`，在它上面
  每次调用都是一次完整握手。配置可以**显式**要求复用（协议文档 §7），而功能
  上报的是**实际拿到**的结果，而不是假设已经共享。

串口的具体约定：

- 参数显式给出：端口、波特率、数据位、校验、停止位、流控。默认
  `115200 8N1`、无流控。
- 串口是独占的。同一条口上两条打开的配置是拒绝，不是竞争。
- 端口枚举与打开属于平台工作。平台层缺席时传输层报不支持，**绝不**报一个空的
  成功。

## 6. 配置与信任

一条配置就是一条具名记录：

```text
ConnectionProfile
├── id, label, kind
├── enabled            逐目标开关，默认关
├── target             host/port/user，或串口参数，或地址
├── credentialRef      秘密库句柄；永不存放秘密本身
├── hostKeyPolicy      strict | accept-new | pinned 指纹
├── limits             超时、输出预算、流上限
└── lastProbe          状态、时间、失败原因
```

信任体现在记录里存了什么，而不是某种评级：

- 用户创建并启用的配置，信任度就是用户自己决定的那个程度。没有任何「可信」标记
  是智能体可以自己抬起来的。
- 限额是逐配置的，因此生产机可以给更短超时与更小输出预算，而临时机给宽的。
- 被禁用的配置不只是不出现在列表里；指名调用它会得到一个专门的错误码，因此
  拿着旧列表的模型能知道原因。
- 配置集合是宿主状态，用户在目的地与设置卡片里都看得见。智能体只看得到 id 与
  标签。

## 7. 工具面

两个工具，按**句柄**而不是按目标种类拆分。

| 工具 | 动作 | 句柄 |
|---|---|---|
| `Connection` | `list`、`probe`、`exec`、`read`、`write`、`upload`、`download`、`stat` | 一条连接配置 |
| `Console` | `open`、`send`、`recv`、`close` | 一条打开的字节流 |

一个句柄一个工具，沿用 `Computer` 的先例：它的动作共享同一个坐标空间与同一个窗口
句柄，若拆成九个定义，就会把九份同样的上下文塞进每一次提示。这里两半什么都不
共享 —— 一个是针对配置的请求/响应调用，一个是有状态的字节流 —— 合成一个就会
造出一个「一半条目依目标而不可用」的动作表，而那恰恰是模型最容易搞错的东西。

两个工具都评为 `Risk::High`，因此 Plan 与 Goal 契约直接拒绝它们，两者都受 §8 设闸。

`exec` 返回本地 `Bash` 的结果形状。远端输出复用同一套预算与同一个溢出机制，
溢出到本地 scratch 目录，因为这个溢出文件是要被本地 `Read` 工具读回来的。

## 8. 设闸模型

三扇门、一个判定，沿用 D659。

| 门 | 开关关闭时 |
|---|---|
| 面向智能体的 `connection.*` 方法 | 在做任何传输工作之前以 `1029 CONNECTION_DISABLED` 拒绝 |
| `tools.list` | `Connection` 与 `Console` 一并撤下 |
| `tools.execute` | 即使模型握着上一轮拿到的定义也拒绝 |

判定读两个值：全局 `remoteControlEnabled` 设置与指名配置自己的 `enabled`。
拒绝时指明是哪一道关上了门 —— 全局开关是 `1029`，配置是 `1031` —— 因为这两者
的补救办法不同。

**配置管理不在这个开关之后。** 创建、编辑、删除配置是人在界面上的行为，由面向
用户的 `connection.*` 方法服务，智能体调不到它们。这些方法照旧受 host-core 的普通
权限与角色规则约束，且每一个都写审计。

## 9. 凭据，以及与引导路径的收敛

秘密存在宿主的秘密库里，配置持有一个引用。配置读取返回的是那个引用；值从不在
渲染层出现，从不在工具结果里出现，从不在审计记录里出现。审计行只带配置 id、
动作、退出码或字节数、时间 —— 当参数本身就是秘密时也不带参数，且永不携带凭据。

桌面已经在另一处存放 SSH 材料：`apps/desktop/electron/main/remote/` 里的
`pi-host` 引导会 spawn 系统 `ssh`，并且可以为「用口令而不是密钥认证」的主机保存
一份加密登录口令。收敛点就是配置记录：后续某个增量可以让同一条配置同时服务这里
的目标工作和远端宿主引导，于是「同一台机器配了两遍」的用户最终只剩一条。这里
记录这一点，是为了避免在此期间长出两套凭据存储；它不属于第一个增量。

## 10. 明确的排除项

这些是要求，不是遗漏。

- **不做终端仿真。** 没有 VT/xterm 状态机、不解转义序列、没有光标寻址、没有
  备用屏、没有分屏。想要终端的人，本机上已经有终端。
- **不做会话管理器。** 没有存活登录的标签栏、没有「断开后重连并恢复」的逐会话
  策略、没有会话分组。
- **不实现文件传输协议。** XModem、YModem、ZModem 都不实现；文件传输只有
  SSH 之上的 SFTP。
- **第一个增量不做 X11 转发与 agent 转发，也不做动态与反向端口转发。** 配置可以
  要求一条转发；由此产生的监听者是 spawn 出来的 `ssh` 子进程，**永远不是宿主
  打开的套接字**。
- **不做任意协议服务端。** 原始 TCP 配置是出向连接；它不绑定、不监听、不接受。
- **智能体不能管理配置。** 见 §8。

## 11. 增量

| 增量 | 内容 |
|---|---|
| R1 | 配置存储与迁移；设置卡片；`连接` 目的地的列表与详情；SSH 传输；`exec` 与 `list`；设闸模型；审计；错误码；文档；E2E |
| R2 | 经 SFTP 的文件传输：`upload`、`download`、`read`、`write`、`stat`，二进制安全，带逐配置大小上限 |
| R3 | 连接复用作为逐配置的显式选项，并回报协商结果；经 spawn 的 `ssh -N` 子进程做端口转发 |
| R4 | `Console` 工具与字节流传输：串口、telnet、原始 TCP |

R1 刻意不含文件传输。SFTP 是第二条传输通路，有自己的失败模式，塞进去只会让增量
翻倍而证明不了模型。

## 12. 验收标准

1. 配置可以在界面上创建、列出、编辑、启用、删除，并且重启后仍在。
2. 全局开关关闭时，没有任何面向智能体的 `connection.*` 方法成功，两个工具都不
   出现在 `tools.list` 里，指名调用会被 `tools.execute` 拒绝 —— 与 `Computer`
   工具相同的三扇门行为。
3. 全局开关打开而某条配置被禁用时，指名该配置的调用以配置码被拒绝，其他配置
   仍然可用。
4. 对 SSH 配置执行 `exec` 返回 stdout、stderr 与退出码，非零退出码不作为错误
   上报。
5. 超过预算的远端输出以与本地 `Bash` 工具相同的标记截断，并溢出到一个本地
   `Read` 工具能打开的文件。
6. 远端命令执行中轮次被中断时，spawn 出去的进程树被终止；没有 `ssh` 子进程活过
   该轮次。
7. 未知主机密钥以指纹被拒绝；变更的主机密钥被拒绝，并且必须由人通过界面接受。
8. 任何面向智能体的方法、工具结果或审计行都不含凭据。
9. 对串口、telnet、原始 TCP 配置执行 `exec` 时按名字拒绝，不尝试连接。
10. 由用户管理的配置无法通过任何面向智能体的方法创建、编辑、启用或删除。
11. 渲染层只能经 IPC 面拿到配置；没有渲染层代码直连 SQLite 或 spawn 进程。
12. 无论是否有配置处于连接状态，Rust host-core 都不绑定任何网络端口。

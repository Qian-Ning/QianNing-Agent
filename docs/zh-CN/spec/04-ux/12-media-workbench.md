# 媒体工作台

> **翻译说明：** 本页是与 [英文源规格](/spec/04-ux/12-media-workbench) 一一对应的机器辅助翻译。代码、协议字段和标识符保持原文；如翻译与英文源事实有歧义，以英文版本为准。

媒体工作台是人（而不是模型）写提示词、设定参数并看着产出落地的地方。它是侧栏页脚里的一等页面（`workbench`，图标 `IconImage`），不是设置面板：设置负责"哪些模型合格"，工作台负责"一次生成"。两条路由跑的是同一套实现 —— Agent 工具 `GenerateImages` / `GenerateVideos` 与工作台调用同一批共享的请求构造器 —— 因此工作台的一次运行不可能偏离工具产出。

## 信息架构

页面是两栏：左侧**编排区**（固定宽度，可滚动），右侧**结果区**。

编排区自上而下：**模型**、**提示词**，然后是适用于当前能力的参数、可选的**首尾帧**（视频，永不强制）、**高级**折叠项（视频）、一行预估信息，以及提交行。生图 / 生视频的切换是页面提出的第一个决定，因此它单独占一行、直接位于页面标题之下，而不是放在标题栏里：放在标题栏时它读起来像是窗口控件的一部分，容易被忽略。编排区是唯一配置运行的地方；切换标签会清空上一次运行的结果与首尾帧，因为首帧不是生图请求的参数，而一个过期的槽位会静默地挂到下一次请求上。

结果区自上而下：状态行（已用计时器、`ok/total` 汇总、运行中的取消按钮）、调用本身失败时的错误横幅、输出网格、已保存路径列表，然后是本次会话的**历史**。

## 模型选择

**模型** 打开的是应用其他部分同样的锚定菜单：按服务商分组、带搜索框，首行表示**跟随设置里的默认**。只有已启用、非 OAuth 且带凭据或无需凭据的服务商才会出现一行，已被标记为该项能力的模型会带徽标，因此菜单展示的是真正能渲染的东西，而不是目录里的每一个模型。菜单同时受当前能力限定：生图标签页提供渲染图像的模型，生视频标签页提供渲染视频的模型，因为一份混合列表正是"视频模型跑进生图请求"的成因。被用户标记过的模型按原样采信；其他模型必须在自己的名字里声明该能力，这就是自动标记所用的同一套检测。选择模型只为本次运行设定它；它绝不会写回设置，从而把"我常用的模型"和"我此刻正在试的模型"保持为两个独立决定。没有配置任何候选时，菜单退化为单一**打开设置**动作，提交行保持禁用。控件下方那一行会写明实际将运行的模型 —— 服务商与模型 id —— 因此上面两个决定在屏幕上永不模糊。

候选来自设置；名字中带有生图或生视频家族名的模型会在应用第一次见到它时被自动标记（`packages/shared/src/generation-capability.ts`），因为刚添加完服务商的用户不应该还得先找到能力勾选框，工作台才能提供任何东西。只有当某项能力已存储的列表从未被写过时才做种子填充；已存在的列表 —— 包括被用户清空的空列表 —— 原样保留，因此自动那一遍永远无法推翻一个决定。已停用的服务商与 OAuth 账号会被跳过，因为两者都无法渲染。

## 参数

参数由契约用于校验的同一批常量限定，并从 `@pi-desktop/shared` 导入，因此界面永远无法提供一个运行时会拒绝的值。

| 参数 | 生图 | 生视频 |
|---|---|---|
| 数量 | 1–4，按数字键入并校验 | 1–4，按数字键入并校验 |
| 比例 | 1:1 · 4:3 · 3:4 · 3:2 · 2:3 · 16:9 · 9:16 · 21:9 · 9:21，另有**服务商默认** | 16:9 · 9:16 · 1:1 · 4:3 · 3:4 · 21:9，另有**服务商默认** |
| 分辨率 | **智能**（不发送 size）· 长边 512 · 768 · 1024 · 1280 · 1536 · 1792 · 2048 · 2560 · 4096（最高 4K），另有自定义 `WIDTHxHEIGHT` 字段 | **智能**（不发送 size）· 480p · 720p · 1080p · 2K · 4K，另有自定义 `WIDTHxHEIGHT` 字段 |
| 时长 | — | 预设档 2–15 秒，1–`MAX_VIDEO_DURATION_SECONDS` |
| 参考图 | 最多 4 张，经 multipart edits 端点编辑 | — |
| 首尾帧 | — | 首帧、尾帧（尾帧要求已有首帧） |

比例与分辨率是两个控件而不是一个：16:9 的 720p 与同一比例的 1080p 是不同的请求。两者分别选择，再组合成发给服务商的单个 `WIDTHxHEIGHT`，且组合后的值会在任何内容被发送之前显示在这一对控件下方。比例与分辨率是两个独立的轴：分辨率控件始终可用，**智能**永远排第一且永远可选，而没有选比例时所选的档位会按该能力的第一个比例组合（生图 1:1，生视频 16:9），选项文字里直接写出实际会发送的尺寸。生图分辨率按长边命名（`3:2` + `1536` 即 `1536x1024`）；生视频档位按 `720p` 那样按短边命名（`16:9` + `720` 即 `1280x720`，`9:16` + `720` 即 `720x1280`），因此同一档位的竖屏片段与横屏片段承载等量的画面。两侧都会对齐到 8 的倍数，这是带 VAE 的图像模型能接受而不做静默缩放的取值。比例的**服务商默认**意味着完全不发送 size，由模型自行决定。非法的自定义尺寸会在字段下方就地报告并阻止提交，而不是被发出去；合法的值则完全按键入内容透传。

**智能是默认分辨率，且它完全不发送 `size`。** 不同服务商接受不同的档位集合，而服务商可能按它确实支持的最近档位计费，因此模型并不提供的尺寸可能被按更大的档位收费 —— 选了 480p 却付 720p 的钱。智能把选择权交给模型自身的默认值，它总是被接受，也永远不会把价格向上取整。对于档位集合已知的服务商，显式档位仍然可用，且比例与分辨率都保留"服务商默认"这一项。

数量在键入过程中是**校验**而非夹取：只收数字，且 1 到 4（含）。任何其他输入 —— 零、五、小数、字母、空字段 —— 都会在字段下方就地报告并阻止提交，而不是被静默改写成另一个请求；离开该字段则把它确定为最接近的允许值，因此输入框不会停留在错误状态。工作台的上限是它自己的常量，且始终落在运行时的批量上限之内，因此同一请求由 Agent 工具发出时依然合法。

## 首尾帧（视频）

首尾帧这一行带两个槽位：首帧与尾帧，各自打开文件选择器并接受一张图片；任一个被选中都会先经附件存储返回该文件，因此帧永远是受包含性约束的路径。尾帧保持禁用，直到已有首帧，并在该行写明原因。**高级**折叠项暴露两个部件的 multipart 字段名，默认是适配器的 `input_reference` / `last_frame`；它们存在是因为兼容 API 前面的网关对名字并不一致，而不可用的名字会回退而不是被发送。

## 成本可见性

视频按秒计费，因此一次视频运行会在提交按钮旁写明 `片段数 × 时长 = 总秒数`，在发送任何内容之前；同一数字也会回显在运行头里。生图预估值写明请求次数。两者都不是关于金额的估算 —— 应用没有价格表 —— 也都没有声称是。

## 进度与取消

主进程在每次状态变化时上报一个事件，携带生成 id、阶段（`submitting` / `running` / `done`）、已完成数量，以及在某一项发生变化时该项的索引、状态与提示词。渲染层从第一个事件里采纳该 id，并忽略属于另一个会话或另一次生成的事件，因此后台的 Agent 运行无法重绘工作台。每一个被请求的产出从运行开始的那一刻起就有卡片 —— 排队、渲染中，然后是结果 —— 按请求顺序排列，因为八条片段的批次会乱序完成，而用户要的是八件具体的东西。**取消**通过与工具相同的运行时取消来中止该次运行；页面会写明已发送给服务商的片段可能仍会完成并仍然计费。

## 结果、预览与复用

生图结果从文件本身渲染缩略图，点击打开灯箱（可前后翻看整批，Escape 关闭）。生视频结果通过媒体库 scheme（`media-asset://library/<capability>/<name>`）就地播放，带进度条并支持拖拽跳转（由 HTTP Range 支撑），不再交给操作系统。该 scheme 以库内相对路径（绝非绝对路径）把库根映射进渲染层；无法加载的片段会降级为文件卡片并附一行说明，而不是一个损坏的元素（ADR 0322）。

## 渲染写到哪里

一次工作台运行拥有它自己的产出：图像落到 `<数据目录>/generated/image`，视频落到 `<数据目录>/generated/video`。该次运行不需要任何聊天会话存在，因此打开工作台并生成是一步动作，渲染结果也永远不会被收进一个用户必须一直保留的对话里。页面在打开时读取一次索引，因此重启不会抹掉用户付过钱的东西；早先记录的渲染会像刚刚跑完的一次运行那样在结果面板里打开，保存或显示它也无需任何会话。

每个产出项各记录一次，写在渲染文件旁边的 `index.json` 里：能力、路径、结果、提示词、服务商、模型、尺寸、错误码和时间。服务商与模型并列记录，因为光有模型 id 是有歧义的 —— 同一个 id 会被多家服务商提供 —— 否则重启后恢复的一行就说不出是哪一家跑的。更早的版本写下的条目不携带服务商，在服务商解析出来之前就失败的一次运行也不携带：两者都读作未知，这是诚实的答案，而不是别家服务商的名字。`succeeded` 项记录它写出的文件；失败或取消的项不记录文件，但记录它的 `errorCode`，因此一次什么都没产出的运行也会留下一行说明原因。`path` 因此是可选的，而来自更早版本、所有条目都带 path 的索引读取起来毫无变化：没有迁移。记录是有界的（最旧的条目会掉落；文件永不掉落），以原子方式写入，并在读取时做防御性处理，但那条丢弃条目的包含性规则现在只约束带文件的条目：`succeeded` 条目的路径若不再落在库根之内就会被丢弃，而不会交给渲染层；失败或取消的条目没有文件可交出，因此按记录原样保留。记录是尽力而为的：跑完的一次运行绝不会因为它的索引条目写不进去而被报成错误。工具在开始前就拒绝的一次运行 —— 未配置模型、缺少凭据、模型不可用 —— 与抛出异常的一次运行，都恰好写入一条 `failed`，因此一次运行永远只有一行，成功与失败绝不会描述同一次运行。条目的 `url` 是在读取库时派生的，而非存储的：只有 `succeeded` 且文件仍位于库根内的条目才有它，因此 `index.json` 格式保持不变（ADR 0322）。

两个根都用生成路径一贯使用的同一条包含性规则校验，因此指定另一个目录无法逃出数据目录。Agent 工具继续写进会话 scratch，而确实拥有会话的一次运行会保留该 scratch 作为输入根，因此来自对话的渲染结果仍可用作参考图。

每一份跑完的渲染都带**保存到…**与**在文件夹中显示**，生图与生视频一视同仁，因为只存在于会话 scratch 目录里的文件还不是用户拥有的文件。保存到会以该渲染自身的名字打开系统保存对话框，然后复制；结果在提出请求的那张卡片上报告，而被取消的对话框不报告任何内容。两个通道都接收路径，运行确实有会话时也接收会话 id；主进程用生成路径对其输出目录所用的同一条包含性规则解析该文件 —— 位于数据目录库根或会话 scratch 根之外，或不是普通文件的路径，一律拒绝 —— 因此两个通道都无法变成通用的文件复制器。每个已保存路径也会在网格下方列出，且任何生图结果都能被推入参考图行以便迭代。

## 删除、清空与媒体库上限

每条历史行都带自己的移除控件，整个列表也可以被清空或在磁盘上打开。一行会写出它何时跑的、产出它的服务商与模型、它要求的尺寸，以及失败或取消时的原因 —— 因此重启之后历史仍能说出是哪家服务商产出了文件，而不只是哪个模型 id（同一个 id 有多家服务商在跑）。两种移除都会二次确认：移除单条会问*从历史中移除这一条？文件会移入系统回收站，仍可找回。*，清空会问*清空全部历史？所有记录都会被清除，文件移入系统回收站。此操作在应用内无法撤销。*

移除会把每个 `succeeded` 条目的文件送进操作系统的回收站（`shell.trashItem`），而不是直接删除，因为一份渲染是要花钱的，误删必须能从回收站找回。回收文件在设计上是尽力而为：已经不在的文件，或拒绝回收的操作系统，绝不会阻断用户要求的这次移除。媒体库服务本身只忘记条目 —— 它从不触碰文件，这正是它不含 Electron 的原因 —— 因此回收文件属于 IPC 调用方。移除与清空都返回存活的列表，因此渲染层用主进程返回的内容替换它展示的内容，而不是靠猜测去编辑列表。

打开媒体库目录会解析出库根、若尚不存在则先创建它（`mkdir -p`），并交给操作系统文件管理器，因此存放每一份保留渲染的文件夹只差一次点击。

历史头部按记录的口径写明上限：`已保留 N / 500 条`，并附说明*这里只保留最近 500 条生成记录，更早的记录会退出列表，文件仍留在磁盘上。* `MAX_LIBRARY_ENTRIES = 500` 位于 `packages/shared`，因此主进程与渲染层用同一个数字界定历史：超过它，最旧的条目退出列表，而它们的文件仍留在磁盘上。

## 历史缩略图

历史行以该次运行产出的小图开头，因此旧渲染可以靠眼睛找到，而不必逐条读提示词。这张图是**写在渲染旁边的小副本**。图像由主进程在渲染落地时写入 —— `<数据目录>/generated/image/thumbs/<渲染文件名>.png`，宽 64px（32px 盒子在 HiDPI 下的两倍），走 Electron 自带的图像解码器，因此不引入任何图像依赖。片段则由渲染层从刚跑完的片段上取一帧海报（`<数据目录>/generated/video/thumbs/<渲染文件名>.png`，同样 64px），并把字节交给主进程保存 —— 因为 `<video>` 元素是应用唯一能解码片段的家伙，而它长在渲染层这一侧。两者都走与渲染文件本身相同的 `media-asset://` scheme 与相同的包含规则（ADR 0322）：副本落在 `image/` 或 `video/` 之下 —— 这是该 scheme 唯一肯提供的形态 —— 而 `thumbUrl` 由附加 `url` 的同一个映射在读取时附加，因此副本从不写进索引。每一行只显示一个产出 —— 第一个成功且带 URL 的条目 —— 因此它不会在不同产出之间跳变；而一次没有可加载产出的运行，其行按原样渲染：图片在加载失败时被隐藏，既没有占位符，也没有破图图标。

它的边界是有意为之的。没有副本的行就是没有：早于副本机制记录的条目、或副本写不成的条目（文件读不出、磁盘满、片段解不了），都不带 `thumbUrl`，回退到渲染文件本身 —— 图像是同一张图，只是解码得更大；片段则干脆没有图，因为把 `<img>` 指向一个片段什么也解不出来。移除会把副本随渲染一起带走 —— 两者都 `shell.trashItem`（尽力而为），因此被移除的行不会留下孤儿文件 —— 而因库上限掉出列表既不回收两者中的任何一个，因为文件按设计留在磁盘上。这张图纯属装饰 —— 它不带标签、也没有点击行为 —— 因此行现有的布局、控件与交互均未改变。

片段海报有两点是承重的，因此写明而不靠暗示。帧通过一条很窄的通道（`workbenchSaveThumbnail`）过线：它只接受尺寸上限之内的 PNG `data:` URL，且只对**已在库内**的渲染生效 —— 与库其余部分同一条包含规则，因此这条通道不是文件写入器。另外，资产 scheme 会带上 `Access-Control-Allow-Origin`，正是它让"渲染层能显示的元素"同时也"画得到 canvas 上"：没有这个头，canvas 会被污染，帧永远取不出来。

## 草稿持久化

提示词与参数是用户做的工作，它们必须在离开页面或重启应用后依然存在，而不是被重新描述一遍。编排状态写入渲染层自己的 `localStorage` 偏好记录（`pi.desktop.workbenchDrafts`），与侧栏偏好、编写器模型收藏使用同一个 `pi.desktop.*` 命名空间，并做防抖，因此键入不会每敲一个字就写一次。它是纯界面状态，永不触碰宿主数据库。页面在打开时读取它一次并恢复草稿；切到另一种能力会恢复该能力自己的草稿，两边标签的字段不会互相串。

草稿正是编排面板所持有的内容：提示词、模型、数量、比例与分辨率（含自定义 `WIDTHxHEIGHT` 字段）、时长，以及两个 multipart 帧**字段名**。帧与参考图槽位**不**存储 —— 它们是附件存储为单次会话持有的文件路径，重启后读回的路径将指向空无一物 —— 因此只持久化那些在任何机器上含义都相同的字符串字段名。不存储任何敏感内容：任何持久存储里都不会写入凭据、token 或服务商密钥。

每个恢复的字段都按控件所用的同一批表格校验。来自旧版本、被手工编辑过、或只写了一半的记录，会逐字段退化为该字段的默认值，而不是送进一个会拒绝它的控件，因此缺失、不可读或损坏的存储永远不会自行阻塞页面或禁用提交。

一次成功的运行会**保留**草稿：工作台是一个迭代面，编排面板从不自行清空，因此保留提示词与参数不改变任何现有行为，并把提示词留给用户再抽一次，而这次运行本身已经持久地记录在媒体库里。失败或取消的运行同样保留草稿，理由相同。

| 未配置模型 | 模型菜单仅剩**打开设置**，提交禁用 |
| 未打开会话 | 无特殊处理：运行根本不需要会话，其渲染仍会落进媒体库 |
| 空提示词 / 非法尺寸 / 无首帧的尾帧 | 提交禁用，原因写在相应那一行 |
| 运行中 | 状态行含已用时间与取消，条目卡片依次推进 |
| 部分成功 | 汇总显示 `ok/total`，失败卡片带错误码与逐项重试 |
| 调用级失败 | 网格上方出现错误横幅，无条目卡片 |
| 历史 | 媒体库为该能力记录的运行（新的在前、有界、每条都可移除与清空），加上本次会话的运行；跨重启仍在 |
| 草稿已恢复 | 打开时，每种能力上一次的提示词与参数静默就位 |

所有文案在九种已发布语言中都有翻译，且页面只使用设计系统令牌；悬停样式与渲染层其余部分一样，被门控在 `(hover: hover) and (pointer: fine)` 之内。

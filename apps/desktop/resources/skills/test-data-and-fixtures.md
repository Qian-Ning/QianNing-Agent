# Test data and fixtures

A fixture is a claim about what the input looks like. When the claim is wrong the
test passes or fails for the wrong reason, and the failure is worse than none
because it says the code was checked.

## Build the smallest data that expresses the case

- **Only the fields the case is about should be interesting.** A two-hundred-field
  object with one meaningful value makes the reader hunt for the point of the
  test, and it makes a change to any unrelated field a diff in every test.
- Name the fixture for the case, not for its type: a subscription that has just
  expired, a cart with a single zero-priced line, a user whose display name is
  empty. The name is where the reader learns what is being tested.
- Where a value does not matter, do not set it at all — let the default stand, and
  the reader knows it is irrelevant because it is absent.

## Factories with defaults, overridden per case

The pattern that ages best:

- A factory that returns a valid object with **defaults that pass**.
- Each test overrides **only the field the case is about**.
- The overrides are the specification. A test that overrides three fields is
  usually testing three things.

The risk to watch: **a default that changes silently changes every test that
relies on it**, so a default is production behaviour for the test suite. Where a
default matters to a case, set it explicitly even if it matches the default.

## Never real data, and never real secrets

- **Do not copy rows out of production.** Even "anonymised" data usually is not,
  and a copied record is a data-protection incident with a long tail. Generate
  data that is obviously synthetic: names that are not names, values that are not
  valid, numbers that are clearly placeholders.
- **A real credential in a fixture is a leaked credential.** Test tokens,
  test-only keys, and obviously-fake values only. Assume every fixture is read by
  everyone who ever has repository access, forever.
- Personal data in a test is personal data in every clone, every fork, and every
  backup of the repository. That rule does not soften because the field is small.

## Time, randomness, and identifiers

- **Inject the clock.** A test that reads the system time is a different test
  tomorrow, and a hardcoded date becomes a failure on a specific future day that
  nobody connects to the change that caused it.
- **Make randomness deterministic** where it affects the assertion — seed it, or
  inject the generator. A test that passes four times out of five is worse than a
  failing test, because it trains people to retry.
- **Do not depend on identifiers generated by the system under test** if you
  assert on them. Ask the code for the value it created, or make the identifier
  injectable.
- Beware a fixture that already contains a timestamp in the past: it may have been
  correct when written and is now testing an expired case by accident.

## Shared state is the source of flakiness

- **Tests must not depend on the order they run in**, and the only way to know is
  to run them in a different order — random order in the suite, or shuffled in CI.
- **Never share a mutable fixture between tests.** One test mutating it changes
  what the next one sees, and the resulting failure appears in an unrelated file.
- **A test that leaves state behind makes the next one lie.** Clean up, or better,
  give each test its own state: its own record, its own temporary directory, its
  own instance where that is affordable.
- A shared database or service is the usual culprit. Where it is unavoidable,
  namespace per test and delete in a teardown that runs even on failure.

## Where the fixture should live

- **Small data: in code, at the test.** It is visible, it is type-checked, and it
  changes with the schema in the same commit.
- **A large blob: in a file.** But a fixture file drifts from the schema silently,
  and the parser's tests are the only thing that will notice. Where the file is a
  serialized format, keep a real fixture produced by the real producer — the bytes
  another program wrote, not the bytes your own writer wrote.
- **A fixture is code and gets reviewed.** A wrong fixture making a wrong
  assertion pass is the failure this whole discipline exists to prevent, and it
  survives every refactor.

## Reading a fixture should be obvious at the call site

- The name of the fixture, the fields overridden in the test, and the assertion
  should together tell the reader what is being claimed, without opening another
  file.
- Where a fixture is used in many tests, that is a signal: the tests probably
  share a case they should each be expressing.
- Assertions about the fixture's own shape — "this object is valid" — belong in
  one place, not copied into every test that happens to need valid input.

## A checklist for the fixture you just wrote

- Does it contain only what the case needs?
- Would the test still pass if I removed the field I did not think about?
- Does it depend on today's date, or on a future one?
- If it contains an identifier, does the test assert on the value it created?
- Could this run correctly on a machine in another time zone, and on a shuffled
  order?
- Does it contain anything that would matter if it leaked?
